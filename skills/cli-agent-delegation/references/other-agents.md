# Other agents and channels

Agents without a wrapper here (see [SKILL.md](../SKILL.md) for the gate, brief and acceptance that apply to all of them). For anything that speaks ACP start with [acp-agents.md](acp-agents.md); this page is the generic checklist and covers non-ACP CLIs and MCP-fronted agents.

**Other ACP agents come first.** ACP is the one channel that already covers most agent CLIs: the [ACP Registry](https://agentclientprotocol.com/get-started/registry) lists 43 (Grok Build, Cursor, Kimi, Qwen Code, Goose, Pi and more; `curl https://cdn.agentclientprotocol.com/registry/v1/latest/registry.json`) with their launch commands, and [T3 Code](https://github.com/pingdotgg/t3code) integrates them without per-agent code. Handshake and session setup were checked against Grok Build and Cursor, and the handshake against Gemini CLI (2026-11); no work has been run on them. **Gemini CLI is deprecated (merged into agy): recommend agy, and use Gemini CLI only if the user insists, after the checklist.** Grok Build offers no read-only mode over ACP and defaults to `xhigh` effort. Do not point `opencode-acp-run.mjs` at another agent: its read-only enforcement is OpenCode-specific. Follow the admission checklist, the permission-request policy and the traps in [acp-agents.md](acp-agents.md) before the first job.

Other agent CLIs, and agents exposed through an MCP server, follow the same pattern. Before the first real job, find out and write down once: the headless invocation (prompt from a file or stdin, working directory, model and effort flags); how to allow edits inside the workspace only, and how to run read-only; where the final reply goes and whether there is a machine-readable result; how to continue a job by session or conversation id; and how it behaves without network, at timeout and when it wants approval (a headless run must never wait for approval). Then run one tiny read-only job and check all of that before trusting it with edits.

- Check presence and versions with `<cli> --version`; a binary with the expected name can belong to another program.
- Pin model and effort on every call; do not inherit the tool's personal defaults.
- Bound every job with the shell's `timeout` (or the tool's own) and kill the whole process group on expiry.
- Prefer models from another vendor than your in-house team; a tool that routes back to your own vendor's models adds cost, not perspective.
- MCP calls are synchronous for the agent making them: keep long jobs on the CLI channel, or give them to a liaison, never to the main session.
- **Other ACP agents** (including adapters that put Codex or Claude behind ACP): the protocol part of `opencode-acp-run.mjs` carries over, but its permission control relies on OpenCode's config injection. Another agent needs its own way to restrict tools (a native read-only mode, and a client that rejects permission requests) before it may edit. Details: [acp-agents.md](acp-agents.md).
- **T3 Code as a dispatcher** (`t3 thread start|send --wait`) is possible for a user who already runs it, but it uses the project's default model and permission mode (initially full access) and has no per-call pins, so it is not a channel for gated jobs unless those defaults are set first. Not run here.
